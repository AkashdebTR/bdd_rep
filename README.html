1. Framework Overview

This framework automates browser-based authentication flows against SauceDemo or a configured web application. Scenarios are written in Gherkin, executed by Reqnroll, and backed by Microsoft Playwright page objects and NUnit assertions.

Reqnroll keeps test intent readable to product and engineering teams. Playwright provides browser control, locator auto-waiting, URL/navigation waits, screenshots, and traces. NUnit provides test discovery, result status, category filtering, and TRX output. Page objects keep application selectors and operations out of step definitions.

Each scenario receives its own Playwright process, isolated browser context, and page. The current suite does not enable scenario parallelism.

4. BDD and Scenario Numbering

Every executable scenario has exactly one stable scenario-ID tag matching TC followed by at least three digits. IDs are authoritative in tags; the title repeats the ID so NUnit output is also traceable. IDs are permanent identifiers, not list positions, NUnit runtime IDs, or retry counters.

Feature: User authentication

  @smoke @TC001
  Scenario: TC001 - Valid user can log in
    Given I am on the login page
    When I log in with valid credentials
    Then I should see the inventory page

CommonUtils.GetScenarioId requires exactly one matching tag. Extent entry names, scenario logs, screenshot names, and trace names carry the ID. The current feature has no Scenario Outlines. If an outline is added, each generated example must have a distinct stable ID; do not reuse one outline tag for all example executions without extending the ID model.

Before adding a scenario, search existing feature files for @TC tags, reserve the next unused ID, and keep it when scenarios are reordered or renamed.

Get-ChildItem Features -Filter '*.feature' -Recurse | Select-String -Pattern '@TC[0-9]+'

5. Configuration Management

appsettings.json contains non-secret defaults. Environment variables override ordinary settings using double underscores. Credentials use TestCredentials__Username and TestCredentials__Password; an optional, ignored logincredentials.json is supported for local work and is not copied into build output.

{
  "BaseUrl": "https://www.saucedemo.com/",
  "Browser": { "Engine": "chromium", "Channel": "chrome", "Headless": false },
  "Timeouts": { "ActionMs": 10000, "AssertionMs": 5000, "NavigationMs": 30000 },
  "Diagnostics": {
    "CaptureScreenshotOnFailure": true,
    "TraceMode": "retain-on-failure",
    "ScreenshotDirectory": "TestResults/artifacts/screenshots",
    "TraceDirectory": "TestResults/artifacts/traces"
  },
  "Reporting": { "OutputDirectory": "TestResults/Reports" },
  "Retry": {
    "Enabled": false,
    "MaxRetries": 1,
    "CaptureScreenshotOnEveryFailedAttempt": true,
    "TraceOnRetry": true
  }
}

The real file also retains ArtifactDirectory as a fallback for screenshot/trace directories. ConfigReader.Load() returns one cached validated settings snapshot. The base URL must be absolute HTTP or HTTPS; only Chromium accepts a channel.

Credentials

Set credentials in a developer shell or CI secret store; never commit them:

$env:TestCredentials__Username = "your-test-user"
$env:TestCredentials__Password = "your-test-password"

Optional local JSON shape:

{ "Username": "your-test-user", "Password": "your-test-password" }

Both credentials must be present together. Missing credentials do not prevent non-login scenarios from starting; a login step reports an actionable error. The values are not written to reports.

Retry settings

Important: runtime-configurable retries are not supported for these generated Reqnroll NUnit methods. NUnit 4.3.2's retry attribute is method-level and static. When Retry.Enabled is true and MaxRetries > 0, scenario setup fails explicitly. Do not enable this combination expecting retries. MaxRetries is validated from 0 through 5; enabled with zero retries executes once. Screenshot-per-retry and trace-on-retry settings are reserved and currently have no retry attempts to control.

7. Execution Lifecycle

  1. Reqnroll starts a scenario and the hook validates its unique scenario-ID tag.
  2. The hook loads settings, starts/gets the shared report entry, and rejects an unsupported dynamic retry configuration.
  3. Playwright starts; the configured browser engine/channel launches; the hook creates one isolated context and page for the scenario.
  4. When trace policy is retain-on-failure, tracing starts before Gherkin steps and records action information, screenshots, and DOM snapshots without source collection.
  5. Step definitions call page objects; page readiness combines DOMContentLoaded with a meaningful locator. Locator operations keep Playwright's auto-wait behavior.
  6. On failure, the hook captures a screenshot and exports the trace before closing the context. Diagnostic failures are recorded as secondary errors; the scenario's original failure is preserved.
  7. The hook closes context, browser, and Playwright resources. The report records outcome and evidence; the shared report is flushed once in Reqnroll's AfterTestRun lifecycle.

Passing scenarios retain no trace file. Skipped and setup-failed scenarios are mapped to report status when Reqnroll/NUnit invokes the corresponding hooks.

Open the newest HTML report directly in a browser. Open a trace with the Playwright viewer:

powershell.exe -ExecutionPolicy Bypass -File .\bin\Release\net10.0\playwright.ps1 show-trace TestResults/artifacts/traces/<run-id>/<trace-file>

Artifacts can contain application data. Apply suitable access controls and retention policies when publishing them from CI. Reports and artifacts are ignored by Git.

There is no automatic retry attempt evidence because dynamic retries are unavailable. A failed scenario produces one failure screenshot/trace according to the normal diagnostics settings, not one per simulated retry.

9. Prerequisites and Setup

  • .NET 10 SDK.
  • Google Chrome installed for the checked-in default Browser:Channel = "chrome".
  • Access to the configured target application and valid credentials for login scenarios.

From the repository root in PowerShell:

dotnet restore
dotnet build --configuration Release --no-restore
# Configure credentials in this shell or a secure CI secret store.
$env:TestCredentials__Username = "your-test-user"
$env:TestCredentials__Password = "your-test-password"
dotnet test --configuration Release --no-build --logger "trx"

The full build/test sequence above was run successfully in this workspace. The current Chrome channel was available locally. If changing to Playwright-bundled Chromium, set Browser:Channel to null or remove it in appsettings.json, then install the supported browser after building:

powershell.exe -ExecutionPolicy Bypass -File .\bin\Release\net10.0\playwright.ps1 install chromium

For Firefox or WebKit, set Browser:Engine, clear Browser:Channel, and run the matching install firefox or install webkit command. Those engines are implemented but were not exercised in the latest verification. The process-scoped execution-policy option above was verified here; it does not change machine policy.

11. Coding Standards and Best Practices

  • Document reusable public APIs with XML comments; explain why in inline comments only where the reason is not obvious.
  • Use descriptive PascalCase APIs, camelCase locals, underscore-prefixed private fields, and Async suffixes for asynchronous methods.
  • Keep selectors and application operations inside page objects. Keep step definitions as readable orchestration.
  • Prefer role, label, and test-ID locators. The framework configures data-test as the Playwright test-ID attribute.
  • Prefer Playwright's built-in auto-waiting. Do not use fixed sleeps or network-idle as a general readiness rule.
  • Keep credentials out of source, reports, and logs. Use environment variables or the ignored local file.
  • Each scenario owns its browser context. Do not enable parallel execution without verifying test-account and runner lifecycle isolation.
  • Do not edit generated Reqnroll C#; change the feature and let the normal build regenerate it.

Adding a scenario

  1. Choose an unused stable TC### ID and add exactly one matching tag and the same prefix to the scenario title.
  2. Add readable business steps to the feature.
  3. Implement missing bindings in StepDefinitions and delegate browser behavior to the relevant page object.
  4. Build and filter by TestCategory=TC###; verify report and artifact IDs.

12. Troubleshooting

Common symptoms and checks
SymptomCheck
Browser launch failsThe default uses installed Chrome through the Chromium chrome channel. Confirm Chrome is installed, or clear the channel and install bundled Chromium using the generated Playwright script.
Configuration validation failsCheck that BaseUrl is absolute HTTP/HTTPS, browser engine is chromium/firefox/webkit, channel is only set for Chromium, and timeout values are positive.
Login credentials are missingSet both TestCredentials__Username and TestCredentials__Password; check spelling and shell scope. Never paste secrets into logs or commit them.
Scenario ID setup failureEnsure every scenario has exactly one @TC### tag. Keep the title prefix synchronized.
Locator timeoutCheck the page state, selector, configured action/assertion timeout, and the failure screenshot/trace. Keep selectors page-specific and stable.
Report missingConfirm scenario hooks ran, the reporting output directory is writable, and inspect test output for an Extent warning. Check Reporting:OutputDirectory.
Screenshot or trace missingScreenshots require a failed scenario, an available page, and CaptureScreenshotOnFailure=true. Traces require TraceMode=retain-on-failure and a created context.
Retry setup errorExpected for Retry.Enabled=true with MaxRetries > 0 in the current runner. Turn it off or use zero; do not interpret this as an actual retry.

13. Limitations and Future Improvements

Implemented

  • Stable scenario IDs in Gherkin tags/title, NUnit category filtering, report names, and failure artifact filenames.
  • Extent Spark reporting, failure screenshots, configurable retain-on-failure tracing, and unique artifact names.
  • Typed settings and scenario-scoped browser/context/page lifecycle.
  • Reusable path/metadata utilities and timeout-backed Playwright waits.

Not implemented

  • Dynamic NUnit retries from configuration, flaky-pass handling, and per-retry evidence. Current NUnit/Reqnroll integration fails closed when retries are requested.
  • Scenario Outline examples with unique per-example IDs. The current convention requires one ID tag per generated scenario, and no outlines are present.
  • Parallel scenario execution. It remains disabled.
  • Firefox/WebKit runtime verification and a provider-specific CI workflow.
